# Pumba 1.5.0 "agent-ready pumba"

Status: **approved 2026-10-29**, recommendations D1–D6 accepted. Revised after a peer review with Codex.

This is a design document. It fixes contracts (CLI, events, interfaces, module placement) and leaves file layout and internal helpers to the implementer.

## 1. Goals and non-goals

An agent or a script can run Pumba and then:

1. **Know what happened** without parsing logs: a result event stream with a versioned schema.
2. **Know when a fault is active**, so it can start its probes at the right time.
3. **Find what a run left behind** after a crash, and **check that targets are clean**.
4. **Preview a run** (targets and the exact `tc`/`iptables` commands) without touching anything.
5. **Discover the CLI** as JSON.
6. **Receive events remotely** (webhook), without pumba-side scripting.
7. **Bound a run in time** (`--max-duration`), so a lost or forgotten interval run stops by itself.

Non-goals (1.6.0+): `pumba revert`, the Inject/Revert/Verify handle refactor, MCP server, cgroup-limit stress, logrus→slog, urfave/cli v3, moby client, DNS/L7, Kubernetes.

Hard constraints:
- No existing invocation changes meaning: same flags, defaults, text output and exit codes. The one deliberate exception is that dry-run no longer sleeps for `--duration` (§3.4).
- The archfit module graph stays as it is (§2).

## 2. Architecture fit

Current approved graph: `cmd → {pkg_chaos, pkg_container, pkg_runtime}`, `pkg_chaos → {pkg_container, pkg_util}`, `pkg_runtime → {pkg_container, pkg_tc}` (visible only to `cmd`). `pkg_container`, `pkg_tc` and `pkg_util` depend on nothing. Every new line of code lands in one of these modules, and no edge is added.

| Concern | Lives in | Why there |
|---|---|---|
| Run ID, event types, event sink interface, outcome/error codes | `pkg_chaos` | chaos produces the outcomes; cmd consumes them |
| Emitting per-target events | `chaos.RunOnContainers` | already the single fanout point every action uses |
| Writing events to stdout, webhook delivery | `cmd` | all I/O stays in the composition root |
| Fault-state and plan value types, sidecar label names | `pkg_container` | shared vocabulary between chaos and runtimes |
| Reading netns state, building the commands it plans | `pkg_runtime` + `pkg_tc` | the code that runs `tc`/`iptables` today is the only one that knows their argv |
| tc/iptables argv building and output parsing | `pkg_tc` | pure functions; runtimes already depend on it |

Archfit traps and how this design avoids them. Each was verified with `archfit policy can-import` on master; all of these edges come back `denied`.

| Trap | Avoided by |
|---|---|
| chaos imports a runtime to find tagged artifacts | Netns state is read through one new `container.Client` method. Leftover sidecars are found with the existing `ListContainers` + a label filter. |
| a new `pkg/events` outside every module, or core calling into cmd | Event types and the sink interface go in `pkg/chaos`. cmd only implements sinks. |
| chaos rebuilds tc/iptables argv, or imports `pkg/tc` | The runtime returns the plan, using the same builder it executes with. |
| HTTP inside chaos | The webhook is a cmd-side sink. |
| guessing which run owns a qdisc | It isn't guessed: the qdisc is reported as unattributed (§3.2). |

Local archfit note: the installed CLI is v3.3.0; the repo config targets engine v3.4.0. It runs with a scratch copy of the config that drops `module_review`, and with `GOCACHE` under `$TMPDIR`. The App's `archfit/gate` (required by ruleset `archfit-gate`) is the gate of record.

## 3. Design per feature

### 3.1 Run ID

- Global `--run-id`: names this invocation and tags everything it creates. Generated when absent (short random hex). A user-supplied value is validated (short, `[A-Za-z0-9_.-]`, safe in labels and iptables comments); an invalid value is a usage error.
- One ID per process, shared by every `--interval` tick.
- The run ID flows to runtimes as a field on the existing request value objects (netem, iptables, stress). The empty value means untagged, which keeps direct callers and tests valid.
- `GlobalParams` carries the run ID and the event sink. Lifecycle and stress actions should keep the `*GlobalParams` they receive instead of copying its fields. Today they copy, and AGENTS.md has to warn to forward `MaxTargets` by hand; every new field would repeat that trap.

### 3.2 Tagging and `pumba status [--check]`

**Tagging.**
- Every sidecar Pumba creates (netem/iptables on Docker, Podman and containerd; stress sidecars) carries labels for run ID, target container ID and kind, in the existing `com.gaiaadm.pumba.*` namespace, next to today's skip label. The containerd netem sidecar has no labels today.
- Every iptables rule carries `-m comment --comment pumba:<run-id>`. The comment must be part of both the add and the delete spec. Without `xt_comment`, install fails closed and the error names the cause.
- iptables argv fan-out is duplicated in the docker and containerd runtimes today. It moves into `pkg/tc`, so the comment and (in 3.4) the plan have exactly one source. `pkg_tc`'s description in `docs/architecture.md` widens from "tc command builder" to "tc and iptables commands Pumba runs in a target netns". This is a doc change, not a policy change.

**tc qdiscs carry no comment field.** Root handle `504d:` is a Pumba convention used for ownership checks. It does not attribute the qdisc to a run. Status reports a qdisc with that handle as:
- `pumba-owned` when the topology matches what Pumba installs (netem root, or prio + sfq + netem bands);
- `suspicious` when the handle is present but the topology is not.

Its `run_id` is always `null`.

**`pumba status [--run-id ID] [--check] [containers…]`**
- Selection works as for chaos commands. No selection means all running containers. `--max-targets` applies, because inspection starts one short-lived sidecar per target.
- `status --run-id` is a **filter**, separate from the global `--run-id` (invocation identity). The global flag never filters.
- Per target it reports:
  - iptables rules with a `pumba:` comment (filterable by run);
  - Pumba qdiscs (unattributed);
  - Pumba sidecars labeled with that target's ID (filterable by run).
- Sidecars whose target no longer exists are reported only when no selection is given.
- Every target gets one of three inspection results: `inspected`, `failed` (with error), or `skipped`. Containerd listing currently skips containers it can't read; such gaps must surface as `unknown`, never be ignored.
- Some findings belong to no inspected target: orphan sidecars, containers the runtime could not list, and explicitly named targets that don't exist or aren't running. They go in a **coverage/artifacts payload** on `run.end` for status, so nothing is reported only in text.
- `--check` gives a verdict:

  | Verdict | When | Exit |
  |---|---|---|
  | `clean` | every selected target was inspected, coverage has no gaps, and nothing matched | 0 |
  | `dirty` | an attributable artifact matched: a tagged rule or labeled sidecar for the run (or any run); with no run filter, also any Pumba-owned qdisc | 1 |
  | `unknown` | any of: inspection failed; a target was skipped; a listing gap; a named target is missing; a `suspicious` qdisc topology; with `--run-id`, only unattributed qdiscs found | 1 |

  `clean` is never vacuous: an empty selection is `unknown`, not `clean`.

  The output always carries the verdict; exit codes stay in Pumba's 0/1 vocabulary (see 3.3).
- Text mode prints a short table; `--output ndjson` prints events (3.3).
- Read-only toward faults. It does create and remove short-lived labeled inspect sidecars (kind `inspect`), which status excludes from its own results.

**New `container.Client` method (1):** an inspector that takes a target plus sidecar hint and returns the parsed Pumba fault state of its netns. It is justified because only a runtime can exec in the netns with output capture; `ExecContainer` returns no output. Parsing of `tc qdisc show` / `iptables -S` lives in `pkg_tc`, so the three runtime implementations stay thin. Podman overrides it with the existing rootless guard.

Known limits, documented:
- iptables rules from Pumba ≤1.4 have no comment and aren't found;
- containerd direct-exec stress leaves no container to find;
- containers sharing a netns report the same state.

### 3.3 Result events: `--output ndjson`

- Global `--output text|ndjson`, default `text`. In ndjson mode, events go to **stdout**, one JSON object per line. Logs stay on stderr; `--json` still only changes the log formatter. All combinations are valid.
- One machine format. There is no folded JSON document: an agent that wants one reads the last line (`run.end`). A missing `run.end` means the output is incomplete (crash or kill).

Event schema `pumba.event/v1`. Every event has `schema`, `type`, `run_id`, `time`, `action` (CLI path, e.g. `netem delay`).

| `type` | Meaning | Key fields |
|---|---|---|
| `run.start` | flags parsed, command built | `pumba_version`, `runtime`, `dry_run`, `interval`, `selection`, `params` |
| `target.applied` | the fault is **active** on a target (for one-shot actions: the action ran) | `tick`, `target{id,name}` |
| `target.result` | **terminal** per target and tick, emitted only after revert finished | `tick`, `target`, `started`, `ended`, `status`, `error`, `cleanup`, plus `plan` (dry-run) or `state` (status) |
| `run.end` | the process is finishing | `status`, `counts`, `error`, `events_dropped` |

- `tick` is a monotonic counter per interval iteration, starting at 1.
- `target.result.status`: `ok`, `failed`, `cleanup_failed`, `planned`, `skipped`.
- `run.end.status`: `ok`, `failed`, `partial`, `cleanup_failed`, `no_targets`, `refused`, `usage_error`, `aborted`, plus `clean`/`dirty`/`unknown` for `status --check`.
- `error` is `{code, phase, message}`. `phase` is one of `usage`, `select`, `inject`, `cleanup`, `inspect`, `runtime`. `code` comes from a small stable set: `invalid_argument`, `no_targets`, `max_targets_exceeded`, `runtime_unavailable`, `rootless_unsupported`, `command_failed`, `cleanup_failed`, `timeout`, `canceled`. Agents branch on `code`; `message` is for humans.
- `params` holds the action's typed flag values. It excludes free-text that may carry secrets (`exec` arguments), every global URL/credential/TLS path, and raw argv.
- Versioning: within v1, fields and `type` values may be added, and consumers ignore unknown ones. Renaming, removing or re-meaning a field, or adding a `status`/`code` value, bumps to v2.

Example:

```json
{"schema":"pumba.event/v1","type":"run.start","run_id":"3f9c2a7b1d04","time":"…","action":"netem delay","pumba_version":"1.5.0","runtime":"docker","dry_run":false,"interval":"0s","selection":{"names":["web-1"],"labels":[],"random":false,"max_targets":2},"params":{"duration":"30s","interface":"eth0","time":100,"jitter":10}}
{"schema":"pumba.event/v1","type":"target.applied","run_id":"3f9c2a7b1d04","time":"…","action":"netem delay","tick":1,"target":{"id":"a1b2…","name":"web-1"}}
{"schema":"pumba.event/v1","type":"target.result","run_id":"3f9c2a7b1d04","time":"…","action":"netem delay","tick":1,"target":{"id":"a1b2…","name":"web-1"},"started":"…","ended":"…","status":"ok","error":null,"cleanup":{"ok":true}}
{"schema":"pumba.event/v1","type":"run.end","run_id":"3f9c2a7b1d04","time":"…","action":"netem delay","status":"ok","counts":{"selected":1,"ok":1,"failed":0,"cleanup_failed":0,"planned":0,"skipped":0},"error":null,"events_dropped":0}
```

**Where events come from.**
- `run.start` comes from the shared CLI builder (`NewAction`).
- `target.applied` and `target.result` come from `RunOnContainers`. Each per-target action reports, beyond its error:
  - a cleanup outcome;
  - an optional plan or state;
  - an "applied" signal at the moment the fault becomes active, i.e. between inject and the duration wait.

  The mechanism is the implementer's choice (a returned result struct plus a callback, or similar), but it must stay a single path through `RunOnContainers`.
- `pause` and `stop --restart` revert in a batch after fanout today. They must still emit each target's terminal result only after its own revert: either the runner learns about deferred reverts, or the action reports them back per target. Reporting those targets as `ok` before unpause/restart is wrong.
- `run.end` comes from cmd when the app returns, including usage errors that never reached chaos. cmd derives it from the counted results plus the returned error, using an outcome function owned by `pkg_chaos`.

**Accounting is separate from delivery.**
- Outcome counts and the final status are computed from what actually happened, before any event is queued. A slow or broken sink can never change the result or the exit code.
- Delivery is lossy by design. Each sink (stdout, webhook) has its own bounded queue and writer goroutine, so a stalled consumer never keeps a container paused or delays cleanup.
- Each sink counts its own drops. `run.end.events_dropped` reports the stdout sink's count, which is the one the consumer is reading.
- `run.end` gets a bounded best-effort flush at exit. A closed or blocked stdout can make delivery impossible, so consumers must treat a missing `run.end` as "outcome unknown"; the exit code is still authoritative.

**Interactions:**
- `--interval`: one `run.start`/`run.end` per process; `applied`/`result` per target per tick.
- `--random`, `--limit`: only selected targets produce events; `counts.selected` per run.
- `--max-targets` refusal: no target events; `run.end` `refused` with `max_targets_exceeded`.
- `--skip-error`: failures are still recorded in events.
- SIGINT/SIGTERM: in-flight targets finish cleanup and emit `target.result`; `run.end` is `aborted` unless something failed.

**Exit codes (decision D1).** Recommended: Pumba keeps its documented 0/1 exit vocabulary in every output mode, which is stable and unchanged. The detailed outcome is in `run.end.status` + `error.code`; the "stable codes" are the event codes, not process exit codes. Today's mismatches are kept as they are:
- "no targets" exits 0 (`run.end` says `no_targets`);
- an iptables cleanup failure exits 0 (`run.end` says `cleanup_failed`).

Fixing those to exit 1 consistently is a separate, called-out behaviour change; recommended for 1.5.0, see D2.

### 3.4 Dry-run plan

- With `--dry-run`, every action returns right after planning. Nothing sleeps for `--duration` (today netem/iptables dry-runs sleep the full duration). The meaning (no chaos) is unchanged; only the timing changes, and the release notes say so.
- `target.result` (status `planned`) includes the resolved target. For netem and iptables it also includes the exact commands that would run for apply and revert: `sh -ec <script>` for netem, one `iptables` argv per rule (with the run comment), and whether they run in a sidecar (image) or by exec in the target. Lifecycle and stress plans carry targets and params only.
- In text mode the plan is printed to stdout as short human-readable "would run" lines (target, via, commands). An info-level log would stay hidden at the default `warning` level, so #363 would remain unfixed. This is new stdout output for dry-run invocations: additive, and listed in §4.

**New `container.Client` methods (2):** a plan method next to the netem pair and one next to the iptables pair (the latter takes the add and delete requests, as chaos already does). Each runtime must build the executed argv and the planned argv with the same function, and a test must pin `plan == executed`. Podman overrides both with the rootless guard (dry-run on rootless Podman already fails today).

This is the costliest feature for its value (decision D3). If cut, dry-run still gives resolved targets + normalized params with no interface change, and the argv plan moves to 1.6.0.

### 3.5 Webhook

- Global `--webhook URL`: a cmd-side sink that POSTs each event (the ndjson object) as `application/json`.
- Delivery: best-effort, ordered, bounded queue, short per-request timeout, redirects not followed, one warning to stderr on drop or failure, short flush at exit. No retries and no custom headers in 1.5.0 (tokens go in the URL).
- The URL and the bodies are never logged.
- `--slackhook`/`--slackchannel` stay exactly as they are, not deprecated, with no Slack format for `--webhook`. Slack users keep the log hook; a Slack-shaped result notifier can come later if asked for.
- Security note for the docs: events include container names and IDs, and they leave the host.

Decision D4: Codex recommends deferring the webhook, because `pumba -o ndjson … | <shipper>` already covers external collectors. Kept here because it is in the agreed scope, and the minimal version above is small.

### 3.6 `--max-duration` run budget

- Global `--max-duration DURATION`, default `0` (unlimited). It is a time budget for active chaos and `--interval` scheduling, and a backstop for agents that start a long or interval run and may lose track of it.
- The budget starts before the first tick. When it expires:
  - no new injections start;
  - in-flight work is canceled;
  - the usual detached, separately bounded cleanup runs.
- The run ends with `run.end` status `aborted`, error code `timeout`, exit 1.
- It is **not** a guarantee about residual damage:
  - it bounds execution only while Pumba is alive (no protection against SIGKILL);
  - it does not cap total process wall time, because cleanup may run past the budget;
  - it does not undo `kill`, `rm`, or a `stop` without restart.

  The docs say so plainly.
- Not required, and with no default cap: netem, iptables, pause and stress already require a positive `--duration`, and a mandatory cap would break existing interval runs.
- Implementation: a deadline on the top-level context plus a check before each tick. It must not change cleanup's use of `context.WithoutCancel`.

Considered and deferred: having `status` report containers left paused or stopped by a crashed `pause`/`stop` run. Neither state proves Pumba did it, and the container model reports lifecycle state differently across runtimes. Correct attribution needs durable run evidence (the 1.6.0 handle work).

### 3.7 `pumba schema`

- Prints JSON (`pumba.cli/v1`) describing global flags and the command tree. For each flag: name, aliases, type, default, env var, repeatable, usage. It also lists the event schema version and the `error.code` list. Implemented by walking the urfave app.
- The one flag-type introspection used by `schema` and by `run.start.params` lives in the cli adapter (`pkg/chaos/cliflags`), keeping a future cli v3 swap local.
- Works without a container runtime socket: no runtime client is created for this command.
- Enums/constraints are deferred.

## 4. Compatibility

- Text mode: stdout, stderr, exit codes and messages unchanged, except these deliberate changes, all listed in the release notes:
  - dry-run returns immediately instead of sleeping for `--duration` (§3.4);
  - dry-run prints its plan to stdout (§3.4);
  - an iptables cleanup failure exits 1 instead of 0 (D2, if accepted).
- `--max-duration` defaults to 0 (unlimited), so existing runs are unaffected.
- New runtime footprint:
  - iptables rules gain a comment match (requires `xt_comment`);
  - sidecars gain three labels.
- Both are covered by integration tests on all three runtimes.
- Go API: `container.Client` grows by 3 methods (inspect, plan netem, plan iptables). There are no known external implementers; the release notes mention it.

## 5. Testing approach

- Unit, table-driven, mocks via `container.NewMockClient(t)`:
  - outcome mapping (every `run.end.status`/`error.code`);
  - event contract (literal expected JSON per type);
  - runner emission (parallel/serial/skipped, random, max-targets refusal, no targets, cancel, cleanup failure, applied-before-result ordering);
  - pause/stop terminal-after-revert;
  - tc/iptables argv characterisation (an untagged rule stays byte-for-byte as today) and parser fixtures;
  - plan == executed argv;
  - status verdicts (clean/dirty/unknown, run filter vs unattributed qdisc, skipped containers);
  - non-blocking emission with a stalled writer (outcome and exit code unaffected; drops counted per sink);
  - status coverage gaps and missing named targets → `unknown`;
  - `--max-duration` expiry;
  - schema covers every command and flag type.
- Integration (bats; `jq` added to the test image and local VM deps):
  - per runtime (Docker, containerd, Podman): ndjson sequence;
  - `--json` + ndjson keeps stdout pure;
  - `status` finds a tagged iptables rule and a qdisc from a backgrounded run;
  - `kill -9` mid-run then `status --check` is `dirty`, and after manual cleanup `clean`;
  - dry-run plan returns immediately and leaves no qdisc;
  - `schema` with no socket.
- The existing bats suites must pass unchanged (text-mode regression).
